# Publishable and secret Supabase API keys

The project authenticates to Supabase with the publishable (`sb_publishable_…`) and secret (`sb_secret_…`) API keys, and the legacy `anon` and `service_role` JWT keys are deactivated. The move was forced early by a leaked `service_role` key, but it was due regardless: Supabase deprecates the legacy keys by the end of 2026 and no longer issues them to new projects. The alternative was to regenerate the project's JWT secret, which re-issues both legacy keys and invalidates every session; it would have bought a credential we had to replace again within the year. Legacy and new keys can be live at the same time, so the swap was values-only in Netlify, and deactivating the legacy keys afterwards is reversible — which makes revocation, not re-issuance, the thing that ends a leak. The secret key is named `netlify_production` so it can be revoked alone, and the two Postgres roles are untouched: the publishable key still acts as `anon` and the secret key as `service_role`, so every migration's grants are unchanged.

User access tokens were still signed by the project's legacy shared JWT secret. Migrating to asymmetric JWT signing keys was kept out of the leak response deliberately, so that one failure would have one cause, and tracked as its own issue. It has since been done (2026-09-15): the project signs with an ES256 key, `kid 0b23a31e-9f81-4b48-b429-679fbe2d0abc`, and the legacy shared secret is no longer the signing key. That closes the last thing the leak response left open — rotating a shared secret invalidates every session, whereas an asymmetric key rotates without downtime, because the retired key goes on verifying until the tokens it signed expire ten minutes later.
